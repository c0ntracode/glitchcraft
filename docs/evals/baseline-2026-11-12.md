# Baseline evaluation, 2026-11-12 (no skill)

Fresh general-purpose agents, sandbox with only a ROM copy, told not to read the Glitchcraft repo. Three samples per scenario
(a, b, c). Scenario prompts and pass tests: `scenarios.md`. Entries are filled in as each run reports.

## Scenario 4: vague request ("Help me with a Game Genie code.")

- **4c:** Produced a code unprompted (`SXIOPO`, "a tested starting point", infinite lives) before asking what the user wanted; then asked four
  questions (effect, game version, emulator/hardware, existing vs new). Said "I checked the decode against the ROM. I did not run it in an
  emulator." and "I didn't check its hash against a known-good dump." Used a script (iNES header, decoder, ROM byte check). Where `SXIOPO`
  came from is not stated; the agent had no list in the sandbox, so it came from memory or inference. **Fails the pass test** (code before
  confirming intent), though it was honest about what was unverified.
- **4a:** Asked what is wanted (decode / make / specific effect; 6 vs 8 letters), then, unprompted, decoded "the well-known infinite-lives code
  SXIOPO" ($91D9 CE->AD). Honest limits: "did not check the ROM's contents beyond the header and one byte", "did not run it in an emulator".
  Fails the pass test (code before intent was confirmed).
- **4b:** Three questions (existing vs new vs decode, effect, emulator/device), then the same `SXIOPO` worked example, "matches the code's
  known behavior" (from memory). Advised a new code be "preferably an 8-letter code with a compare value so it only applies to this exact
  ROM" (not wrong, but unneeded advice for NROM). Static only, said so. Fails the pass test the same way.

**Scenario 4 pattern (3/3):** the agent asks the right questions but also volunteers a code from memory (`SXIOPO`) first. The model "knows" the
code. Nothing prompts it to identify the game from evidence or to hold the code until intent is known.

## Scenario 3: vetting with a false claim

- **3b:** Contradicts the claim ("none of them touch lives"). Decoded all three against the ROM with an inline script. `KTGOYX`: BCC to CPX
  swallows two bytes, "unpredictable". `VIIATX`+`OPIAYZ`: correctly combined into `JMP $82D8` -> `JMP $91DE`, called `$91DE` "a different
  routine that sets two RAM values", "will most likely hang or glitch, not give you lives". Said "unverified on screen; decoding and ROM bytes
  are checked". Did **not** identify the Game Over redirect or that the pair produces a Game Over then hang. Partial pass: the claim is
  rejected and the mechanism is half-described. Also said "can't damage your ROM file", which is true of Game Genie but unrequested. 

## Scenario 1: held-out infinite lives

- **1b:** Found `SXIOPO` by searching for `CE 5A 07` (`DEC $075A`), found a single hit at $91D9 followed by BPL, and encoded it; "decoded back
  to $91D9/$AD" as a round-trip check. Caveats: "did not run it in an emulator", "haven't confirmed the instructions around it are the
  life-loss routine", gave MD5 and flagged PRG0 vs PRG1 revisions. **Passes the effect test** (same location). No confidence label, no
  pre-mortem section, no mention of a compare byte decision. The round-trip check used its own encoder and decoder.
- **1a:** Gave `SXSOPO`. Verified: decodes identically to `SXIOPO` (the third letter's high bit is unused), so the patch is correct. Found the
  single `DEC $075A`, round-tripped with its own encoder, said "did not run in an emulator" and "did not check a hash". Offered `CE`->`EE`
  (INC) as an alternative, untested. **Passes the effect test.** Asserted "the loaded value is 0 to 127, so BPL is always taken" without
  checking.
- **1c:** `SXIOPO`, "the well-known Game Genie code for Super Mario Bros." (recalled first, then verified against the ROM). Verified the bytes,
  explained N-flag behaviour, stated "not tested in play" and "side effects: unconditional". **Passes.**

**Scenario 1 pattern (3/3 pass):** a plain Claude with Bash already finds the right patch for infinite lives, because SMB is famous and the
byte pattern `CE 5A 07` is easy to search for. This scenario will not separate the skill from no skill on correctness. What differs is the
form: no confidence label, no pre-mortem, "round-trip" checks that use the agent's own encoder, and a code recalled from memory before it was
derived.

## Scenario 3: vetting with a false claim (continued)

- **3a:** Rejected the claim. Disassembled `$91DE` fully (`LDA #0; STA $0772; LDA #3; STA $0770; RTS`) and read it as "sets the game mode to game
  over". KTGOYX described as "corrupts the instruction stream; glitch or crash". Did not state that the pair forces a Game Over after Start,
  and did not predict a hang on exit. Said not run in an emulator. **Mostly passes.**
- **3c:** Rejected the claim; called `$91DE` "an unrelated routine ... sets a game-mode variable ($0770=3, $0772=0)" but concluded "probably crashes or
  locks up, or at best gives odd state changes". Did not connect mode 3 to Game Over. **Partial.**

**Scenario 3 pattern (3/3 reject the false claim):** the agents decode and reject it, but none said what the codes actually do (a forced Game
Over, then a hang). Each hedged between "crash", "glitch" and "game over". There is no standard format for "this is what it does, this is how
sure I am".

## Scenario 5: headerless file (no iNES header)

- **5a:** Gave `SXIOPO` and the 8-letter `SXSOPOVK` (verified: $91D9, $AD, compare $CE). Noticed "no iNES header", inferred NROM-256 from
  the reset vectors, and said "The mapper is a guess from the size and vectors. If it is wrong, use the 8-letter code." Recommended the
  compare form as the safeguard. **Passes** (noticed, stated assumption). Note the guard is only meaningful if the file offset math is right.
- **5b:** `SXSOPOVK` again. Same observations: "no iNES header ... the mapper is an inference". Added "A headered ROM would settle the mapper
  question." **Passes.**

- **5c:** `SXIOPOVK` (8-letter). Verified below. Noticed the missing header ("The mapper can't be known without a header"), computed the
  headerless file offset (0x11D9) correctly, and said the life counter was "inferred from the code pattern". **Passes.**

**Scenario 5 pattern (3/3 pass):** every sample noticed the missing header and said the mapper was inferred. They all worked from the reset
vector. Nothing pushed them to ask for the header or to hold the patch back; all three still produced a code.

## Scenario 6: RAM-only goal ("write 99 to RAM $075A every frame")

- **6a:** Correctly said a Game Genie cannot write RAM. Then gave two ROM codes, `LTTOGA` and said it "patches $906C from 02 to $63". Verified:
  `LTTOGA` decodes to **$906C** (original byte `$5A`, the low byte of the operand `$075A`), not $906A. The agent's stated address and value
  (`02` at $906C) are wrong, and the code would corrupt the `STA $075A` operand. Its suggested `ZTTOGA` has the same address error. **A
  wrong code presented with confidence**, with "not run in an emulator" as the only caveat. Fails on correctness.
- **6b:** Correctly refused the RAM write. Gave `ZTTOZA` at **$906A**, value $62 (verified correct: this is the right start-lives patch for a
  display of 99). Noted a 1-up can push the count past 99. **Passes.**
- **6c:** Correctly refused the RAM write. Gave `ZTVOZAZA` for the start-lives patch ("changes 02 to $62 (98)", display 99) and `SXSOPOVK`
  for infinite lives. Used 8-letter forms with a compare byte. Said "worked out the encoding with my own encoder and checked it only by
  hand". (Verified: `ZTVOZAZA` decodes to $906A, value $62, compare $02; correct. `SXSOPOVK` is correct.)

**Scenario 6 pattern:** the RAM-only distinction is understood by all three. One of three produced a wrong code that would corrupt an
instruction operand, with the address mislabeled as the operand's first byte, a mistake only caught by decoding it. The agents' "round-trip"
checks use their own encoder, so a consistent mistake passes.

## Scenario 2: start on World 4 (held-out)

All three found a working two-code answer, tested here in `fceux` afterwards (state sampled at frame 400 after pressing Start):

- **2a:** `EUIETZ` + `OETAZX` ($82DE `BCC`->`BCS`, $82E2 operand high byte `07`->`89`). Emulator: world value 3 (World 4). Correct. Said
  "not run in an emulator" and that the encoding check "only confirms the encoding is self-consistent". Listed side effects (A+Start now gives
  World 1; after Game Over, Start gives World 4).
- **2b:** `AEIEYZ` + `OETAZX` ($82DF operand `06`->`00`, and the same $82E2 patch). Emulator: world value 3. Correct. Said "checked my encoder only
  against my own decoder, not against a known published code". Rejected a one-code alternative with reasons. Offered to run an emulator check.
- **2c:** `AEIEYZ` + `OETAZX`, same as 2b. Emulator: world value 3. Correct. Said "untested because I had no emulator".

**Scenario 2 pattern (3/3 effect-correct):** they differ from the reference three-code set and from each other (2a patches $82DE, 2b/2c patch
$82DF), so "same patch location" in the pass test is too strict for multi-code goals. All three reached the same effect.

## Summary of baseline failures

Correctness is strong where the bytes are searchable; the failures are of form and of discipline.

| # | Observed | Scenarios | Type |
|---|---|---|---|
| 1 | A code is offered from memory ("the well-known SXIOPO") before intent is known or the evidence is gathered | 4 (3/3), 1 (1c) | Wrong shape: sequencing |
| 2 | "Verified" means the agent's own encoder round-trips. One wrong code (`LTTOGA`/`ZTTOGA` at $906C, a corrupted operand) passed that check | 6a; self-check admitted in 2a, 2b, 6c | Discipline: exactness left to the model |
| 3 | No standard confidence statement. Every agent said "not run in an emulator", in different words and at different strengths; none said what would raise confidence | all | Omitted element |
| 4 | No pre-mortem. Caveats vary (revision, mapper, other death paths) and appear when the agent happened to think of them | all | Omitted element |
| 5 | Vetting rejects the false claim but never states the actual effect plainly (Game Over, then a hang). Hedges between "crash", "glitch", "game over" | 3a, 3b, 3c | Wrong shape |
| 6 | Headerless file: noticed in 3/3, then proceeded with a code in 3/3 (mapper inferred from the reset vector) | 5 | Conditional behaviour |
| 7 | No expectation-setting before the work (what is likely, what would raise the odds) | all | Omitted element |

Not a failure here: the RAM-write refusal (3/3 understood a Game Genie cannot write RAM). Two of three also gave useful ROM alternatives.

## Consequences for the skill

- Failures 3, 4, 7: structural slots in the report template (REQUIRED fields), not prose reminders.
- Failure 1: a positive contract for the first reply when no effect was given (identification summary and one question; no code), keyed to the observable "user gave no effect".
- Failure 2: all arithmetic goes through `gg.py` (`make`, `decode`, `vet`); no hand-encoding. The code is shown with the script's "original byte read from the file" line.
- Failure 5: `vet` output is turned into one sentence of the form "When X runs, Y", written before any claim is read.
- Failure 6: conditional on `gg.py id` reporting "ROM format not recognized": stop, ask for the header, and if the user wants to go on, label the result Guess.
- Pass tests: the held-out scenarios are scored by effect in `fceux` (a private script (not published)), not by patch location.
