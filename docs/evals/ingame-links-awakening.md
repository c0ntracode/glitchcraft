# In-game check: Link's Awakening (Game Boy), "walk through walls" AF7-168-3B0

Date 2026-11-12. Driver: a private script (not published) (run it with no arguments; about 2 seconds, no display).

## Question

Does a published Game Genie code in a switchable ROM bank (bank 2, $4000-$7FFF) have its published effect in the
real game, and do the emulator's own cheat decoder and Glitchcraft's `gg.py patch-copy --bank N` agree?

## Why this code

Walk through walls needs no enemy, no item and no damage, so it can be shown from a new file with a short scripted
input. The effect is large and visible: Link either stops at the bed or crosses the room boundary. Infinite
health or keys would need scripted combat or shopping. ROM: Rev 2 USA/Europe, SHA-1 5ab63def958728933571c3b4f6af54db14f3f8b2.
Code: `gg.py decode ROM AF7-168-3B0 --bank 2` gives `$7716 value=$AF compare=$B6 original=$B6` (OR (HL) -> XOR A).

## Method

Gambatte (`/usr/lib/libretro/gambatte_libretro.so`) through the shared a private script (not published). Three
runs, identical input, each in a fresh process:

- (a) original ROM, no cheat
- (b) original ROM, `retro_cheat_set` with the code before frame 1 (the core's own decoder)
- (c) `gg.py patch-copy ROM OUT AF7-168-3B0 --bank 2` output, no cheat

Input schedule (frame, button, frames held): 300 START 6 (title); 500 START 6 (to player select); 850 A 6 (file 1);
1100 A 6 (letter "A"); 1150 START 6 and 1250 START 6 (accept name, Marin's house loads); A for 3 frames every 10
frames from 1700 to 2690 (Marin's dialogue); 2750 DOWN 20 (Link gets out of the bed); 2900 LEFT held 400.
These input frames came from trial runs, with screenshots read at each stage.

## Evidence (frame hash / OAM-shadow hash / WRAM hash, first 8 hex of SHA-1; OAM = WRAM $C000-$C09F)

| Frame | (a) unpatched | (b) cheat | (c) patch-copy |
|---|---|---|---|
| 2900 (before walking) | 0381721e / 2cf3d5a4 / 51ac667e | identical to (a) | identical to (a) |
| 3000 | 9e173a6c / 0239d7ae / 565dd2a7 | 0ffc126c / 6d4b4ce4 / 59b6302e | identical to (b) |
| 3100 | 9e173a6c / 0239d7ae / 51204e38 | bd23313f / cde68af1 / 9f948d05 | identical to (b) |
| 3200 | 87373f35 / fa10086d / 9b2172a7 | bd23313f / cde68af1 / 0744fe5b | identical to (b) |

Pictures (in the scratch work directory, regenerated by the driver with `--workdir`): in (a) Link stays in the
house room pressed against the bed and wall at 3000, 3100 and 3200 (the 3200 frame hash differs from 3100 only
by Link's animation). In (b) at frame 3000 the screen is mid-scroll: Link has walked through the left wall and the
adjacent room, with pots, is sliding in. By 3100 (b) and (c) sit in that pot room ("Wow! This looks pretty heavy!"
dialogue box open), a room Link cannot enter by walking left without the code.

## What it proves

- With AF7-168-3B0 applied through Gambatte's decoder (b), Link walks through the bed and wall and the game scrolls
  to the next room; unpatched (a) he does not. That is the published effect, seen in play.
- (b) and (c) are identical at every checkpoint in frame hash, OAM sprites and all 8 KiB of WRAM. So the core
  decodes the code into the same bank-2 byte at $7716 that `patch-copy --bank 2` writes.
- The three runs are identical at frame 2900, so the divergence comes from the code, not from input or timing.

## What it does not prove

- Only this code (bank 2) was played. The other published codes (infinite health $6098, rupees $5FB0, keys $7464,
  invincibility $6D8F bank 3) were verified by compare byte only; none was played here.
- It does not show the code applies only while bank 2 is mapped, nor the behaviour in other maps (dungeons, water).
- Gambatte is one emulator; real hardware or a Game Genie device were not tested.
- The cheat was set before frame 1 only; setting it mid-game was not tested here.

## Unverified

- Which game routine reads the patched byte (the effect is observed; the mechanism is inferred from the OR (HL) ->
  XOR A change at $7716, not traced).
- Whether the same input frames work on another ROM revision (only Rev 2 was run).
